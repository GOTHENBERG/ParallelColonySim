# Инструменты разработки и открытый процесс

Документ фиксирует минимальный набор инструментов для самостоятельной открытой игры на Rust/Bevy. Первый Cargo workspace уже создан; CI workflow включён для проверки форматирования, Clippy и сборки.

## Решения для первого Cargo workspace

| Область | Базовый инструмент | Когда подключать |
|---|---|---|
| Версия Rust | `rust-toolchain.toml` с stable и компонентами `rustfmt`, `clippy` | При создании workspace; фиксировать канал и target, не pin-ить ежедневный номер компилятора без причины |
| Форматирование | `cargo fmt --all -- --check` | В каждом PR |
| Статический анализ | `cargo clippy --workspace --all-targets -- -D warnings` | В каждом PR; предупреждения исправлять, а не массово подавлять |
| Сборка и тесты | `cargo check --workspace --all-targets` и `cargo test --workspace` | На Windows и Linux в GitHub Actions после создания первого crate |
| Проверка зависимостей | `cargo deny check` с политиками лицензий, advisory и источников | До подключения сторонних crate и затем в CI |
| Повторяемые бенчмарки | `criterion` для сценариев из `sim_testkit` | Вместе с первым измеримым simulation benchmark |
| Трассировка стадий | `tracing` и `tracing-subscriber`; необязательный Tracy exporter за feature flag | Когда появятся стадии тика и нужно будет разделить время вычислений и ожидания |
| Проверка графа Bevy schedule | `bevy_mod_debugdump` как локальная dev-зависимость | При диагностике неожиданной сериализации систем; не включать в релизную сборку |

Поначалу достаточно встроенного `cargo test`; `cargo-nextest`, snapshot-testing и дополнительные property-testing библиотеки не добавлять, пока время CI или сложность инвариантов не покажут, что они нужны. Бенчмарки запускать в release-профиле на сохранённых сценариях и сравнивать одинаковые seed, размер карты, количество жителей и worker count.

## CI для GitHub

После появления workspace настроить GitHub Actions для pull request и push в основную ветку:

1. Матрица Windows и Ubuntu на закреплённом stable toolchain.
2. Кэш Cargo registry/build cache; кэш не считать доказательством корректности сборки.
3. `cargo fmt --all -- --check` и `cargo clippy --workspace --all-targets -- -D warnings`.
4. `cargo check --workspace --all-targets` и `cargo test --workspace`.
5. `cargo deny check` после добавления конфигурации `deny.toml`.
6. Бенчмарки не блокируют обычный PR на старте; отдельный ручной или периодический workflow публикует baseline, версию компилятора, CPU, seed и параметры сценария.

Первый CI должен запускаться на минимальном headless crate без GPU и окна. Визуальную сборку Bevy проверять отдельной job, когда её системные зависимости будут одинаково доступны на runner-ах. Не задавать жёсткий порог миллисекунд до снятия базовой производительности на зафиксированном сценарии.

## Открытый процесс проекта

Перед первым внешним вкладом добавить в корень репозитория:

- `CONTRIBUTING.md`: установка Rust/Windows dependencies, команды форматирования и проверок, правила небольших PR.
- `CODE_OF_CONDUCT.md`: принятую версию Contributor Covenant с контактным способом сообщить о проблеме.
- `.github/ISSUE_TEMPLATE/bug_report.yml` и `feature_request.yml`, а также pull request template.
- `SECURITY.md`: приватный канал раскрытия уязвимостей и поддерживаемые версии.
- `LICENSE` уже содержит GPL-3.0-or-later для исходного кода; `NOTICE` и лицензии игровых assets добавлять по мере появления материалов.

Исходный код опубликован публично под GPL-3.0-or-later. Эта лицензия допускает коммерческое использование, но требует сохранять GPL-условия для распространяемых производных версий. Это не означает, что автор проекта планирует коммерциализацию. Для графики, музыки, шрифтов и других будущих assets нужно отдельно проверять права и совместимость лицензий. Не включать исходники, графику, тексты, названия или иные закрытые материалы RimWorld.
